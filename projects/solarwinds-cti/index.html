Executive Summary

The SolarWinds SUNBURST campaign (MITRE C0024) represents one of the most significant supply-chain compromises in recent history. This report analyzes the campaign's tactics, techniques, and procedures (TTPs) and provides actionable detection engineering guidance for security operations centers (SOCs).

Key Findings

  1. The campaign exploited trust at multiple layers: software distribution, authentication, identity, and cloud infrastructure.
  2. Behavioral detection provides more durable defensive value than relying exclusively on static indicators of compromise (IOCs) — consistent with the Pyramid of Pain model, under which artifacts tied to attacker behavior (TTPs) are far costlier for an adversary to change than hashes, IPs, or domains.
  3. Five key post-compromise behaviors were validated through practical lab testing: suspicious PowerShell execution, scheduled task creation, WMI activity, authentication anomalies, and logging tampering.
  4. Detection requires correlation across endpoint, network, identity, and cloud telemetry.
  5. Attribution to Russia's SVR is High confidence at the government-assessment level; the public does not have access to all underlying intelligence, so this report treats attribution as informative context rather than an independently verified finding.

This report demonstrates the application of cyber threat intelligence (CTI) analysis to detection engineering, with practical validation in a home lab environment.

Introduction

The SolarWinds supply-chain compromise (also known as SUNBURST) was discovered in December 2020. Attackers inserted malicious code into legitimate Orion software updates, which were then distributed to approximately 18,000 customers. A smaller subset of these victims experienced follow-on post-compromise activity.

This report examines the campaign through a CTI analytical framework, answering seven key intelligence questions (KIQs):

  • KIQ 1: What was the Initial Access?
  • KIQ 2: What happened after Initial Access?
  • KIQ 3: Which TTPs were strategically important?
  • KIQ 4: Which IOCs remain useful?
  • KIQ 5: How confident is attribution?
  • KIQ 6: What can defenders detect?
  • KIQ 7: What intelligence gaps remain?

The report follows a structured analytical process:

Raw Intelligence → Validated Facts → Assessments → Confidence → Intelligence Gaps → Impact → Detection Opportunities → Lab Validation.

Intelligence Gaps

  1. How attackers initially compromised SolarWinds build infrastructure
  2. Exact initial-access path for each victim
  3. How every compromised credential was originally obtained
  4. Scope of stolen session-cookie/SAML abuse across the victim population
  5. Exact victim-level attack timelines
  6. Complete relationship between all malware/tool components
  7. Exact amount and destination of exfiltrated data

These gaps represent the boundaries of public knowledge and highlight the importance of continuous intelligence collection and analysis.

Impact / "So What?"

The SolarWinds campaign demonstrates that a sophisticated intrusion can exploit trust at multiple layers — software distribution, authentication, identity, and cloud infrastructure. Consequently, defenders should not rely solely on malware signatures, software reputation, or password-based authentication monitoring; effective detection requires behavioral correlation across endpoint, network, identity, and cloud telemetry.

Pyramid of Pain: This preference for behavioral detection over static indicators maps directly onto David Bianco's Pyramid of Pain — hash values and IP/domain indicators sit at the base of the pyramid and are trivial for an adversary to change, while TTPs sit at the apex and are the most costly for an adversary to alter. The detections built later in this report were deliberately chosen because they target mid- to upper-pyramid behaviors rather than the campaign's now-defunct IOCs.

Key Impact Areas

  1. Supply-Chain Compromise: A trusted software update can become an attack delivery mechanism.
  2. Code-Signing Trust: A valid signature should not automatically be treated as sufficient proof that software is safe.
  3. Multi-Stage Intrusion: Removing the initial malware does not necessarily mean the entire intrusion is contained.
  4. Credential Abuse: Attackers using legitimate credentials can generate activity that resembles legitimate administrative behavior.
  5. Cloud Identity Abuse: Identity infrastructure itself can become a persistence/access mechanism.
  6. Defense Evasion: Attackers can intentionally reduce defender visibility.
  7. Static IOC Limitations: Historical IPs/domains/hashes provide value for retrospective hunting but may become obsolete.
  8. Behavioral Detection: Behavioral indicators provide more durable detection value.
  9. Cross-Domain Detection: Endpoint + network + identity + cloud telemetry should be correlated.
  10. Attribution: Attribution provides strategic context but does not replace detection engineering.

Detection #1: Suspicious PowerShell (T1059.001)

Threat Intelligence Basis: F08 — APT29 used PowerShell during post-compromise operations. PowerShell is a powerful scripting language frequently abused by attackers for execution, reconnaissance, and lateral movement.

ATT&CK Mapping: T1059.001 — Command and Scripting Interpreter: PowerShell

Detection Hypothesis: Suspicious PowerShell patterns including encoded commands, web requests, and execution bypass can be detected and investigated using endpoint and SIEM telemetry.

Telemetry Required: Sysmon Event ID 1 (Process Creation), PowerShell Operational Log Event ID 4104

Lab Simulation

powershell -Command "Invoke-WebRequest -UseBasicParsing https://example.com"

Rationale: This command mimics the behavior of downloading second-stage payloads, consistent with APT29's post-compromise activities (F05, F11).

Telemetry Verification

Before testing the detection, the data pipeline was confirmed operational (Sysmon process creation events flowing to Splunk from a Windows 10 endpoint).

Detection Query Results

The combined detection query identified all suspicious patterns:

index=* EventCode=1 Image="*powershell.exe"
( CommandLine="*-e *" OR CommandLine="*-EncodedCommand *"
 OR CommandLine="*Invoke-WebRequest*"
 OR CommandLine="*.DownloadString*"
 OR CommandLine="*-ExecutionPolicy Bypass*"
 OR CommandLine="*-WindowStyle Hidden*" )
| table _time, host, User, Image, CommandLine, ParentImage
| sort - _time

Investigation

One encoded command was decoded for analysis:

index=* EventCode=1 CommandLine="*-e V3JpdGUtSG9zdCAiQ1RJIFBvcnRmb2xpbyBUZXN0Ig==*"
| eval DecodedCommand=base64decode("V3JpdGUtSG9zdCAiQ1RJIFBvcnRmb2xpbyBUZXN0Ig==")
| table _time, host, User, CommandLine, DecodedCommand

Result: The command decoded to Write-Host "CTI Portfolio Test", confirming this was a harmless test command.

Assessment: While these commands were benign tests, the detection patterns are consistent with attacker behavior documented in the SolarWinds campaign. In a production environment, Base64-encoded PowerShell and web requests would warrant immediate investigation.

Tuning Considerations (False Positives): As written, this query would generate significant noise in most enterprise environments. Recommended tuning before production deployment:
  • Baseline normal PowerShell usage per host/role for 1–2 weeks before enabling alerting.
  • Exclude known-good parent processes (recognized RMM/patch-management agents).
  • Prioritize alerts where PowerShell spawns from an unusual parent (Office apps, browsers, scripting hosts).
  • Treat Base64-decoded content as secondary enrichment, not a standalone alerting trigger.

Detection #2: Scheduled Task Creation (T1053.005)

Threat Intelligence Basis: F10 — APT29 used scheduled tasks in post-compromise activity, including persistence and lateral movement.

ATT&CK Mapping: T1053.005 — Scheduled Task/Job: Scheduled Task

Detection Hypothesis: Scheduled task creation can be detected through Sysmon process creation events for schtasks.exe, and suspicious patterns can be identified through task naming and command-line parameters.

Telemetry Required: Sysmon Event ID 1 (Process Creation), Windows Security Log Event ID 4698

Lab Simulation

schtasks /create /tn "CTI_Lab_Test" /tr "C:\Windows\System32\calc.exe" /sc ONCE /st 12:00 /ru SYSTEM

Detection Query Results

index=* EventCode=1 Image="*schtasks.exe" CommandLine="*/create*"
| table _time, host, User, Image, CommandLine, ParentImage
| sort - _time

Investigation

index=* TaskName="CTI_Lab_Test"
| table _time, host, EventCode, User, TaskName, Command
| sort - _time

Assessment: The task was created as a test and subsequently deleted. In a real intrusion, scheduled tasks are commonly used for persistence, and randomly named tasks with suspicious execution paths would warrant immediate investigation.

Tuning Considerations (False Positives):
  • Filter to tasks running as SYSTEM or a privileged account combined with an unusual /tr target (PowerShell, cmd.exe, LOLBins, or binaries in %TEMP% / %APPDATA%).
  • Flag random-looking task names or names mimicking legitimate Windows tasks.
  • Correlate task creation with the parent process.

Detection #3: WMI Activity (T1047)

Threat Intelligence Basis: F09 — APT29 used WMI for remote execution and lateral movement.

ATT&CK Mapping: T1047 — Windows Management Instrumentation

Detection Hypothesis: WMI activity, particularly process creation via WMI, can be detected through Sysmon process creation events.

Telemetry Required: Sysmon Event ID 1 (Process Creation), Windows WMI-Activity Logs

Lab Simulation

wmic process call create "calc.exe"

Detection Query Results

index=* wmic
| table _time, host, EventCode, Image, CommandLine
| sort - _time

Assessment: WMI is a powerful tool frequently abused by attackers. The wmic process call create command is particularly suspicious as it indicates process creation through WMI, often used for lateral movement. In a production environment, this activity would warrant correlation with other indicators and investigation of the parent process.

Detection #4: Authentication Anomalies (T1078)

Threat Intelligence Basis: F06 — APT29 used compromised credentials to access systems and support lateral movement.

ATT&CK Mapping: T1078 — Valid Accounts

Detection Hypothesis: Unusual authentication patterns, including remote logins and failed logins, can be detected through Windows Security Logs.

Telemetry Required: Windows Security Log Event ID 4624 (Successful Logon), Event ID 4625 (Failed Logon)

Lab Simulation

Remote Desktop login from Ubuntu to Windows 10.

Detection Query Results

index=* EventCode=4624 Logon_Type=10
| table _time, host, Account_Name, Workstation_Name, Logon_Type, Source_Network_Address
| sort - _time

Assessment: Remote logins (Logon Type 10) are common for both legitimate administrators and attackers. In a production environment, this activity should be correlated with:

  • Time of day (outside business hours = more suspicious)
  • Source IP (known vs. unknown)
  • Account (privileged accounts are higher risk)
  • Other activity from the same user/host

Detection #5: Logging Tampering (T1562.001)

Threat Intelligence Basis: F18 — APT29 attempted to reduce security visibility by interfering with security monitoring/logging.

ATT&CK Mapping: T1562.001 — Impair Defenses: Disable or Modify Tools

Detection Hypothesis: Attempts to tamper with logging, including clearing logs or using logging tools, can be detected through Sysmon process creation events.

Telemetry Required: Sysmon Event ID 1 (Process Creation), Windows Event Log Event ID 104 (Log Cleared)

Lab Simulation

wevtutil get-log System

Note: This is a safe query command that does not actually clear logs.

Detection Query Results

index=* wevtutil
| table _time, host, EventCode, Image, CommandLine
| sort - _time

Assessment: wevtutil.exe is a legitimate Windows tool for managing event logs. However, its usage with commands like cl (clear) or disable is highly suspicious. In a production environment, any usage of wevtutil with destructive commands would warrant immediate investigation.

Key Learnings

  1. Sysmon provides critical visibility into process creation and command-line activity.
  2. Windows Security Logs are essential for authentication monitoring but may require audit policy configuration.
  3. PowerShell logging (ScriptBlock) provides deep visibility into executed commands.
  4. Behavioral detection is more durable than static IOC-based detection.
  5. Correlation across multiple data sources provides the most complete picture.

Limitations of Lab Validation

  1. No actual malware execution — testing simulated post-compromise behaviors only.
  2. Limited environment — single-host lab without enterprise complexity.
  3. No network telemetry — Zeek/Suricata not integrated.
  4. No cloud environment testing — SAML/cookie abuse not validated.

Recommendations

For SOC Defenders

1. Enable Comprehensive Logging

  • Enable Sysmon with a robust configuration
  • Enable PowerShell ScriptBlock logging
  • Enable security audit policies for logon, object access, and policy changes

2. Implement Behavioral Detection

  • Monitor for encoded PowerShell commands (-e, -EncodedCommand)
  • Detect Invoke-WebRequest and DownloadString in PowerShell
  • Alert on schtasks /create and wmic process call create, tuned per the false-positive guidance above
  • Monitor for authentication anomalies (time, location, frequency)

3. Implement Correlation

  • Correlate endpoint, network, identity, and cloud telemetry
  • Use a SIEM for central visibility and alerting
  • Build dashboards for suspicious activity patterns

4. Focus on Identity Protection

  • Implement MFA
  • Monitor for token and session cookie abuse
  • Audit federation trust settings
  • Monitor for privileged account usage

5. Develop Incident Response Playbooks

  • Playbook for suspicious PowerShell activity
  • Playbook for credential abuse
  • Playbook for scheduled task creation
  • Playbook for logging tampering attempts

For Threat Intelligence

1. Continuously Monitor

  • Track APT29 TTPs and infrastructure
  • Monitor for new intelligence gaps being filled
  • Track evolving detection opportunities

2. Share Intelligence

  • Participate in ISACs and information-sharing groups
  • Share IOCs and behavioral indicators
  • Contribute to open-source intelligence (OSINT)

3. Update ATT&CK Mappings

  • Regularly review and update TTP mappings
  • Track new techniques and sub-techniques
  • Map detection to MITRE ATT&CK

Limitations

1. No Actual Malware Reproduction

  • The lab validation did not reproduce the actual SUNBURST malware
  • No malicious code was executed
  • Testing simulated post-compromise behaviors only

2. Limited Environment

  • Testing occurred in a single-host lab environment
  • Did not include full enterprise complexity
  • Did not include network telemetry (Zeek/Suricata)
  • Did not include cloud environment testing

3. Limited Scope

  • Only 5 of many SolarWinds TTPs were tested
  • Supply-chain compromise itself was not reproduced
  • Attribution analysis is based on government reports, not independent assessment

4. Telemetry Limitations

  • Some event logs may not be available in all environments
  • Audit policies may vary across organizations
  • SIEM configuration differences may impact detection

5. False Positive Considerations

  • Detection tuning requires production-specific baselining
  • The false-positive guidance in this report is analytic reasoning, not empirical measurement against real enterprise traffic
  • Risk-based scoring would require additional development
